带策略验证的 A 股 LLM 分析系统。

工程结构参考 [daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis)（多源降级 + 定时任务 + 多通道推送），
核心增量是它没有的东西：**一套能证伪的回测与策略验证层**。


---

## 为什么要有这个

DSA 这类项目解决的是「每天怎么把信息推到手机上」，但它不回答一个更前置的问题：

> **这套判断逻辑，在历史上到底赚不赚钱？**

不回答这个问题，看板做得再漂亮也只是把不确定性包装成了确定性。
LLM 给的「评分 65 / 建议买入」背后没有任何统计支撑 —— 它没回测过，
你也不知道样本外会不会直接失效。

本项目把那套工程结构抄过来，然后补上验证层：

```
analyze  →  每天产信号、写台账、推送
backtest →  用历史数据回答"赚不赚钱"
validate →  五大指标打分 + 样本内外一致性 + 显著性检验
compare  →  多策略横向对比，看 LLM 相对朴素规则有没有增量
```

## 快速开始

```bash
# 0) 先体检 —— 30 秒告诉你环境/数据源/LLM 到底哪一环不通
python main.py doctor

# 零依赖即可运行（行情走东方财富/腾讯裸 HTTP 接口，只用标准库）
python main.py analyze --mock            # 离线跑一遍，不调 LLM、不花钱

# 装 pyyaml 后可读取 config.yaml
pip install pyyaml

# 先验证，再看盘 —— 顺序不能反
python main.py validate --strategy five_dim --out reports/validate.md
python main.py analyze --out data/latest_dashboard.md
```

### 为什么第一个命令是 doctor

数据源报错的时候，人最容易做错的两件事是**反复重试**和**凭印象猜**。
`doctor` 把每个源、每个接口单独戳一下，直接区分：
没装 / 没配 token / 积分不够 / 被限流 / 网络不通。

它会真打一次 LLM（**绕过 prompt 缓存** —— 体检命中缓存等于没验证，
那是假绿灯，比红灯更危险），并逐项报告诊断：

```
| 源 | 优先级 | 状态 | 耗时 | 说明 |
|----|--------|------|------|------|
| `eastmoney` | 1 | ❌ 失败 | 1.6s | RuntimeError: Remote end closed connection |
| `tencent`   | 2 | ✅ 可用 | 0.2s | 32 根K线，最新 2026-09-15 收 1272.75 |
| `akshare`   | 3 | ❌ 失败 | 0.1s | ProxyError: push2his.eastmoney.com |
| `tushare`   | 4 | ⏭ 跳过 | — | 未配置 TUSHARE_TOKEN（见 .env.example） |
| `baostock`  | 5 | ✅ 可用 | 0.4s | 32 根K线，最新 2026-09-15 收 1272.75 |
```

```
### 5. LLM 分析器
- 端点：`http://localhost:11434/v1`（本地推理，零成本）
- 模型：`qwen2.5:7b`　超时 240s　max_tokens=200

✅ 连通成功，单次分析 47.0s（未走缓存，快照 2026-09-15）
- 输出：`HOLD`　score=53　confidence=0.70
- 理由：多空指标矛盾，建议观望
- 成本：本地推理，无 API 费用
```

`--skip-limited` 可以跳过 tushare 那几个限流接口（省下每小时一次的配额），
`--skip-llm` 只验证数据源。

### 配置真 LLM

复制 `.env.example` 为 `.env`，`main.py` 会自动加载（已进 `.gitignore`）。
**已存在的环境变量优先**，所以临时覆盖永远赢过 `.env`：

```bash
LLM_MODEL=qwen2.5:7b python main.py analyze
```

三条路线，按成本排序：

| 路线 | 配置 | 成本 | 实测速度 |
|------|------|------|---------|
| **本地 Ollama**（推荐） | `LLM_BASE_URL=http://localhost:11434/v1`<br>`LLM_API_KEY=ollama`（占位，不校验）<br>`LLM_MODEL=qwen2.5:7b` | ¥0 | 16~35s/次 |
| DeepSeek | `LLM_BASE_URL=https://api.deepseek.com/v1`<br>`LLM_API_KEY=sk-...` | 极低 | 1~3s/次 |
| 不配 | — | — | 退回规则模拟器 |

本地模型选型是实测出来的，不是猜的：

| 模型 | 耗时 | 结论 |
|------|------|------|
| `qwen2.5:7b` | 16.6s | ✅ 推荐：JSON 规整、判断稳定 |
| `qwen3:8b` | 92.2s | ⚠️ 思考模式把时间拖了十倍 |
| `qwen3:4b` | 16.6s | ❌ 输出额度被思考耗尽，拿到空串 |
| `llama3.2` | 9.6s | ❌ 判断自相矛盾（`score=2` 却给 `BUY`） |

两个必踩的坑：本地端点要设 `LLM_MAX_TOKENS`（不限输出，小模型能被自己的啰嗦拖死）；
超时会自动放宽到 240s（冷启动加载权重要比热态慢好几倍）。

> **HTTP 401 = Key 无效；HTTP 402 = Key 有效但余额为 0。** 两者完全不同，
> 报错信息里已经写清楚了，别看到 402 就去重新申请 Key。

### 命令一览

| 命令 | 作用 | 典型用法 |
|------|------|---------|
| `doctor` | 环境与数据源体检 | `python main.py doctor` |
| `analyze` | 每日分析 + 写台账与记忆 + 多通道推送 | `python main.py analyze` |
| `analyze --debate` | 用多空辩论出决策（成本约 3 倍） | `python main.py analyze --debate` |
| `debate` | 当场跑一场辩论，并排看两个顺序的裁决 | `python main.py debate --symbol sh600519` |
| `reflect` | 反思结算：把走完验证期的判断变成教训 | `python main.py reflect` |
| `memory` | 查看记忆库 / 模型在某天看得见什么 | `python main.py memory --symbol sz300750` |
| `backtest` | 基础回测 + 交易明细 | `python main.py backtest --show-trades` |
| `validate` | 策略体检（核心） | `python main.py validate --split 0.7` |
| `compare` | 多策略横向对比 | `python main.py compare --strategies ma_cross,five_dim,rsi_reversion` |
| `asof` | 时点审计：这次运行本不该看到哪些数据 | `python main.py asof --as-of 2025-06-20` |
| `ledger` | 查看信号台账 | `python main.py ledger --tail 20` |
| 自检 | 验证验证器本身 | `python tests/selftest.py` |

`backtest` / `validate` / `compare` 都支持 `--as-of YYYY-MM-DD`：指定后只使用
该日期（含）之前可见的数据，并锁定前复权的基准日。回测建议始终显式指定。

带 LLM 的策略另有两个开关：

- `--no-memory`　关掉反思记忆注入。这不是"降级模式"，是**对照组** ——
  「记忆到底有没有用」不该靠感觉，该拿两次同样的回测比出来。
- `--as-of`　记忆也随时点门控：回放到 2025-06-20 那一根时，
  只看得见 2025-06-20 时点已知的教训。

辩论也有一组开关，`analyze` 与 `--strategy debate` 通用：
`--debate-rounds N`（轮数）、`--order bull_first|bear_first`（谁先发言）、
`--no-order-check`（跳过顺序置换检验，省一次调用但结论将**未经检验**）。

## 核心设计：怎么让 LLM 可以被回测

LLM 说的是人话，回测引擎只认机器话。中间必须有一层翻译，
而且这一层要解决七个具体问题 —— 头两个其实是同一件事的两条入口：
未来函数会从**策略**进来（偷看 `bars[i+1]`），也会从**数据**进来
（进来的数据本身就带着 as_of 之后的信息）。
第六条更绕：**记忆本身也是数据，而且它天生带着未来**。

### 1. 未来函数 · 策略层 —— 索引约束 + 反向验证

```python
# 引擎的实际执行顺序
T 日收盘  →  生成信号（策略只能读 bars[:i+1]）
T+1 开盘  →  按开盘价成交（叠加不利滑点）
```

策略接口拿到的 `bars` 是全量数组，但实现方**必须自己切片**。
光靠约定不可靠，所以引擎自带反向验证：把第 i 根之后的 K 线全部乘 3，
如果第 i 根上的决策发生了变化，就说明策略偷看了未来。

实测能抓住故意作弊的策略：

```
[未来函数] TEST 在第 30 根(2025-02-10)：篡改未来K线后信号由 HOLD 变为 BUY
```

### 2. 未来函数 · 数据层 —— 时点门控（`core/asof.py`）

上一条只管得住**策略**，管不住**数据**。数据层泄漏更阴：策略代码看着完全正确
（真的只读了 `bars[:i+1]`），结论却还是错的。三个真实来源：

| 泄漏点 | 后果 | 处理 |
|--------|------|------|
| 数据源按「今天」返回全量 | 尾巴上多出 as_of 之后的 K 线 | 请求区间先钉在 as_of，**未来数据连请求都不发** |
| 降级路径（过期缓存回退）不切片 | 越界的尾巴原样进回测 | 出口统一裁剪，不信任上游 |
| **前复权基准日取「最新」因子** | 把 as_of 之后才发生的除权注入历史价 | 基准日锁到「as_of 可见的最后一个因子」 |

第三条是 A 股特有的。`qfq(t) = raw(t) × adj(t) / adj(最新)` —— 分母那个「最新」
是**今天**。as_of 若落在某个除权日之前，那次除权当时还没发生，却被用来缩放历史价。
实测茅台 2025-06-26 除权：

```
as_of=2025-06-25 口径     1435.86    ← 当天交易所显示的价格
「今天」最新因子口径       1356.28    ← 含 6/26 那次除权
偏差                      -5.54%
```

三条设计原则：

- **出口过滤**　不信任上游。网络来的、缓存来的、过期缓存来的，都过同一道关
- **请求不发**　区间本身钉在 as_of 内，顺带省数据源配额（tushare 有硬限流）
- **丢弃有声**　裁掉多少根 K 线全部记账（`Audit`）；不指定 as_of 时也会明确提示。
  静默的截断比不截断更危险 —— 它会让人以为门控在生效，其实门是虚掩的

```bash
# 当场看一次门控到底挡掉了什么
python main.py asof --symbol sh600519 --as-of 2025-06-20
```

输出会告诉你：请求区间被压缩到哪、裁掉多少根、以及两种复权口径各算出什么价。

验收测试 `tests/test_lookahead.py`（27 项）全部构造真实泄漏场景，
且**每条都带对照组** —— 证明测试场景本身真的含泄漏，不是空转的。

> **这一维的边界，说清楚**：前复权基准日影响的是**绝对价位**和**跨次运行一致性**，
> **不影响日收益率序列** —— 复权是等比缩放，缩放系数在比值里约掉了。
> 真正会吃掉收益的是前两条。别把它当成万能药。

### 3. 反思记忆 —— 但记忆本身也是未来函数（`core/memory.py`）

没有记忆时，每次 `analyze` 都是失忆的：它不知道自己上周说过什么、说对没说过、
有没有在同一个坑里连摔三次。这不是"模型不够聪明"，是工程上没给它记忆。

但把"事后复盘写下的教训"直接喂回下一轮，就等于开卷考试 —— 那份教训是用
决策**之后**的信息生产出来的。所以做法不是回避，是**给它盖一个诚实的日期戳**：

```
learned_date = 决策日后第 horizon 个交易日
             = 「这个结果最早什么时候能知道」
             ≠ 「我什么时候写下它的」
```

于是注入时只有一个判据：`learned_date <= as_of` 才可见。
今天才写下的教训，只要它描述的结果窗口整段落在 as_of 之前，在那个时点就是
合格已知信息；反之，昨天写的教训若讲的是下个月的事，它也进不来。

四条纪律：

| 纪律 | 含义 | 违反后果 |
|------|------|---------|
| **不进早结算** | horizon 没走完就是 `open`，不许用"已经走了 3 天"的数据给 10 天的判断打分 | 给判断硬安一个结论 |
| **日期戳诚实** | 可追溯日期是 `learned_date`；`created_on` 只用于审计 | 今天写的教训没法安全用于三个月前的回测 |
| **未结算不可用** | `open` 状态的判断**不得**作为"你错了"出现在上下文里 | 让模型对着噪声自我修正 |
| **扣留要发声** | 正在验证期的判断必须明说"结果当时还不知道" | 留白被读成"没有教训"，然后它就开始编 |

两类记录，都是 append-only（`decisions.jsonl` / `lessons.jsonl`）：

```
decisions.jsonl   每次 analyze 写一条：「当时凭什么这么判断、当时看得见什么」
lessons.jsonl     每条判断结算时写一条：「结果如何、错在哪一类、教训是什么」
```

**`resolved` 标签是 join 出来的，不是存在字段里的。** 状态由「该 decision 在
lessons 里有没有对应记录」决定 —— 因为 append-only 的价值就在于"当时写下什么
就是什么"，事后回改状态会让台账失去证据资格。

判断记录里刻意存了两样东西，都是为了事后能分清责任：

- `facts_gist`　当时的 RSI / 60 日位置等。**判断错了是方向问题还是位置问题**
  （超买区追高），没有这几个数就永远分不清
- `visible_lessons`　当时上下文里有哪些教训。用来区分**「模型没学会」**和
  **「模型根本没收到」** —— 只看结论，这两种情况长得一模一样

归因是**纯规则**的，刻意不用 LLM 生成教训。理由不是省成本：LLM 写的教训会顺手
带进窗口之外的记忆，而日期戳是按 `learned_date` 盖的，多出来的信息就悄悄漏进去了。
规则文本只由结果数字拼出，信息边界天然等于窗口边界。八类错误画像：

| 类型 | 触发条件 |
|------|---------|
| `chased_high` | 买入且亏损，入场时 RSI≥72 或 60 日位置≥88 |
| `false_breakout` | 买入后最大浮亏 ≤-5% 而最大浮盈 <2%（进去就套） |
| `stop_shaken` | 止损被扫（先触止损）但 horizon 末价格在成本之上 |
| `wrong_direction` | 买入亏损，且不属于上面三种 |
| `sold_too_early` | 卖出后继续上涨 |
| `missed_opportunity` | 观望/回避期间上涨 ≥5% |
| `correct_avoid` | 观望/回避期间下跌 ≥5% |
| `right_call` / `flat` | 判断成立 / 落在 ±2% 噪声区间 |

记账口径统一为「**这次决策带来的价值**」：买入记 `+ret`，卖出/观望/回避一律记
`-ret`（不做多的价值 —— 卖出是躲过下跌，观望是机会成本）。
早先版本把观望记成 0，于是"回避正确"那一行的平均影响永远是 `+0.00%`，
一个有效的统计列变成了装饰。

样本门槛与 `validator.py` 的 `min_trades` 同源：少于 5 条同类不列为"规律"。
2 次里错 2 次不叫规律，叫样本小。

```bash
python main.py reflect                          # 结算 → 写教训 + 错误画像
python main.py memory --symbol sz300750         # 看记忆库
python main.py memory --symbol sz300750 --as-of 2025-06-20   # 看那天模型看得见什么
```

最后一条是这个模块最该被用到的功能：**不猜，直接看**。
它会打印渲染好的上下文全文 —— 也就是模型真正会收到的那段文本，
外加一行注入审计（可见几条、扣留几条、为什么扣留）。

验收测试 `tests/test_memory.py`（116 项）的重心不是"记忆功能正常"，
而是**"这条教训在它不该被看见的那一天，是不是真的看不见"**。
每条判据都配对照组，例如：

```
不泄露被扣留结果的数字          → 通过
对照组：过了可知日那个数字真的会出现  → 通过   ← 证明第一条不是空转
```

> **回测只读记忆，绝不写。** 写了就会污染记忆库，之后再拿这个库做回测
> 就变成自我循环 —— 模型的判断被自己的判断强化，看起来越来越准。
> 唯一的写入入口是 `analyze`。

### 4. 多空辩论 —— 卖点好抄，别让它失控难抄（`core/debate.py`）

让多头和空头各派一个模型互相反驳、再由第三方裁决，这个形态本身很好抄
（参考实现：TradingAgents，arXiv 2412.20138）。难的是**别让它失控**。
所以这一节讲的全是约束，不是功能。

**① 轮数由计数器硬判，模型说了不算。**

```
turn_limit = 2 × max_rounds          # 多空各发言一次算一轮
while len(turns) < turn_limit: ...   # 循环条件里没有模型的位置
```

交给模型自认「聊完了」会同时坏掉三件事：可能无限循环（每多跑一轮都是钱）、
调用次数不可预测（成本没法预算）、每次跑得到不同的过程（**不可复现**）。

这里比参考实现再硬一档：**连「认输」也不缩短辩论**。模型可以输出
`concede: true`，但它只被记进元信息，发言照跑满。否则「辩论多长」这个变量
又回到模型手里了，而且是以最隐蔽的方式 —— 它会以"模型认为可以结束了"的名义
悄悄改变回测的调用模式。

同理，一轮发言**解析失败也算发生过**。把失败从计数里剔掉，轮数就又不定
（失败次数是随机的），而轮数不定等于放弃了可复现。

**② 首轮必须注入「对手尚未发言」占位符。**

不给占位符，首轮模型会凭空虚构一个对手观点再加以反驳，整场辩论建立在幻觉上。
注意占位符是给**整场第一个开口的人**，不是给"每个角色的第一次发言" ——
第二个开口的人面前已经有人讲过话了，再告诉它"对手尚未发言"同样是假的。
`test_debate.py` 里对这两种顺序各测了一遍。

**③ 顺序置换检验：把「不受发言顺序影响」从承诺变成判据。**

参考实现在裁决者的提示词里写了一句「不受发言顺序影响」。那只是**承诺**，
而承诺不能当证据 —— 一个先发言者占优的裁决者也会照着这句话输出，没人看得出来。

所以同一份辩论记录，正序喂一次、反序再喂一次，比较两次裁决：

| 结果 | 处理 |
|------|------|
| 动作与权重都一致 | 认定顺序无关，结论可用 |
| 动作不同 | **结论不可信** → 显式降级为观望，`reason` 里写明两个值 |
| 动作相同但权重漂移 > `0.20` | 同上。两次都判 HOLD，但一次是被多头说服、一次是被空头说服 |

第三条最容易被漏：只比动作会让一半的顺序依赖蒙混过关。反序的实现是把**整段记录
倒过来并整体重编号**（不保留"第 2 轮"字样），这样顺序是两次调用之间**唯一**的差别 ——
`tests/test_debate.py` 里有一条断言直接验证"反序 = 正序的严格逆序"，
还有一条验证"两份 prompt 长度完全相同"，防的是"reverse 其实没生效"这种空转。

用 `--no-order-check` 可以省掉那一次裁决调用，但报告和审计里会明确写
**「未经检验」**而不是沉默 —— 「没验证」和「验证通过」是两个完全不同的状态，
混在一起就是虚假保证。

**④ 失败不许伪装成正常判断。**

裁决解析不出来、动作字段是 `MAYBE` 这种非法值 —— 都显式标记为失败。
这里特意绕开了 `Action.parse`：它对无法识别的输入会**静默回落成 HOLD**，
于是一次失败会被记成一次正常的"观望判断"。失败伪装成正常，比失败更糟。

**成本与用法。** 一次决策 = `2 × 轮数` 次发言 + 2 次裁决。`rounds=2` 就是 6 次调用，
约为单轮的 3 倍，所以它是**可选路径**（`analyze --debate`），不是默认。

更重要的是：辩论被实现成**另一种分析器**（`analyze()` 同形），
于是记忆门控、分数闸门、台账、prompt 哈希缓存全部照用，一行都不用重写。
而且 `debate` 是一个独立的策略名，可以和 `llm` 并排跑体检：

```bash
python main.py compare --strategies llm,debate,five_dim --mock
```

> **「多视角到底有没有增量」是个应该被回测回答的问题，不是应该被相信的问题。**

**⑤ 过程要留档，但别塞进台账。**

裁决只给出一个动作，事后能回答「它为什么这么判」的只有辩论过程本身。
所以全文落 `data/debate/transcripts.jsonl`（append-only，按过程指纹去重），
而信号的 `meta` 里**只放摘要与指纹** —— `meta` 会写进 `signals.csv` 的每一行，
把四段发言塞进去会让台账膨胀到没法用编辑器打开。台账存索引、正文另存，
和记忆库是同构的。

同样地，**回测路径不写这个过程文件**：跑一次回测就往仓库里灌几百条记录，
没人愿意 review。只有 `analyze` 写。

验收测试 `tests/test_debate.py`（132 项）的重心不是"辩论能不能跑"，
而是**"轮数真的不受模型影响吗、顺序检验真的会报警吗"**。
两个方向都配了对照组，缺一不可：

```
无偏裁决者  → 判「顺序无关」      无偏  → 通过
有偏裁决者  → 判「顺序敏感并降级」
```

只有前者能通过，说明不了任何事（一个永远返回 `False` 的空实现也能过）。
只有后者能通过，同样说明不了任何事（一个永远返回 `True` 的过敏实现也能过）。

### 5. 幻觉 —— 只喂事实，不喂原始K线

模型拿到的是算好的指标（`Snapshot`），不是 OHLC 序列。
提示词里明确写死：「严禁引用公司基本面、财报、新闻 —— 你没有这些数据」。
回测时引用训练数据里的基本面，等于未来函数。

数据缺失的字段置 `None` 而不是填 `0`。填 0 会骗模型：
换手率 0% 对活跃个股是不可能的，那个「0」的真实含义是「这个源不提供」。

提示词里还有一条**时点纪律**（比其它规则优先）：模型只活在那个快照日期，
禁止引用训练数据里关于该日期之后的记忆（「后来它涨了」），
也禁止假设后续行情。它知道「后来发生了什么」这件事本身，就是未来函数。
反过来，提示词里**绝不能出现真实今天** —— 那等于告诉它现在是哪一天。

`v3` 起系统提示词里多了一段**历史判断回顾的使用规则**，因为给了记忆就等于
给了它一个新幻觉入口：把历史模式当成对今天的预知。所以写明三条 ——
记忆是参考不是命令；可以推翻但必须在 `reason` 里说明理由
（否则一次正确的推翻和一次无理由的忽视长得一样，没法区分）；
正在验证期内的判断不是失误，不要为了"纠正"它而反向操作。

### 6. 格式失控 —— 解析失败即降级

要求纯 JSON 输出，容忍三种脏格式（裸 JSON / 代码块包裹 / 前后有废话）。
**解析失败一律降级为 HOLD**，绝不让脏数据污染回测。
卖出信号不挂止损目标（A股不能做空，卖出是离场不是开仓）。

### 7. 成本 —— 按 prompt 哈希缓存

LLM 回测的天然障碍是每天都要调一次 API。
缓存键 = `md5(model + 完整prompt)`，提示词模板一改缓存自动失效。
重跑回测零成本，且结果完全可复现 —— 没有缓存就没法做参数调优。

**记忆也在这条哈希里**，这一点不是顺便：如果不进哈希，加了记忆却命中旧缓存，
等于加了没生效，而且完全看不出来。它顺便还保证了"同一时点看得见同样的教训
→ 命中缓存 → 结果可复现"。

提示词模板改动必须同步升 `PROMPT_VERSION`（当前 `v3`）。缓存按内容哈希，
不会误命中旧结果；但版本号是台账里唯一能追溯「那次回测用的哪一版提示词」的线索 ——
不升版，三个月后没人说得清。

> `v1 → v2` 加入时点纪律；`v2 → v3` 加入历史判断回顾槽位。
> 每条判断记录都带 `prompt_version`，换提示词等于换策略，回测要能区分。

## 验证层：三层验证怎么落地

代码化了 a-share-master《验证层-回测框架》的判定标准。

### 五大指标

| 指标 | 及格线 | 优秀线 |
|------|--------|--------|
| 胜率 | >45% | >55% |
| 盈亏比 | >1.5:1 | >2.5:1 |
| 最大回撤 | <20% | <12% |
| 夏普比率 | >1.0 | >1.5 |
| 交易频率 | 5-20 笔/月 | 8-15 笔/月 |

### 第三层才是重点：区分「有 alpha」和「运气好」

| 检验 | 回答什么问题 | 判据 |
|------|-------------|------|
| **样本内外切分** | 参数是不是在拟合噪声 | 前 70% 训练区间 vs 后 30% 区间，单笔期望衰减 >60% 判为过拟合 |
| **显著性检验** | 高胜率是不是样本量太小 | 日收益均值单样本 t 检验，p<0.05 才算显著 |
| **样本量门槛** | 结论成不成立 | 少于 20 笔交易直接判「样本不足」，不给任何有效性结论 |
| **基准对比** | 辛辛苦苦跑赢指数了吗 | 与沪深300 buy&hold 比超额收益 |

不达标的指标会自动定位到具体层级（对应验证层文档的层级诊断表）：
胜率低→选股/执行层，盈亏比低→退出框架，回撤大→风控层，夏普低→战略层。

### 实证：三个朴素策略的体检结果

用 5 只权重股、2024-10 ~ 2026-09 的真实数据跑出来：

| 策略 | 累计% | 笔数 | 胜率% | 盈亏比 | 夏普 | 期望% | 样本内外 |
|------|-------|------|-------|--------|------|-------|---------|
| ma_cross | +5.01 | 40 | 37.5 | 2.17 | 0.12 | +0.468 | +1.16% → **-0.81%** |
| five_dim | +2.93 | 34 | 44.1 | 1.39 | 0.01 | +0.270 | +1.31% → **-2.24%** |
| rsi_reversion | -0.98 | 7 | 42.9 | 1.05 | -1.08 | -0.479 | 样本不足 |
| **沪深300** | **+15.41** | — | — | — | — | — | — |

三个策略全部跑输指数，全部不显著（p>0.6），全部出现样本外期望转负。

**这就是这个工具的价值**：把「看着还行」的策略直接判死。
如果你只做单区间回测，会看到 ma_cross +5% 且盈亏比 2.17 —— 挺像样；
做了样本外切分才知道后半段是负期望。

## 数据源设计

降级链：`tushare → eastmoney → tencent → akshare → baostock → 本地缓存`

tushare 排第一（需 `TUSHARE_TOKEN` + `pip install tushare`，缺任一项自动跳过），
后面的源都**只用标准库**（urllib + json），保证任何干净环境、包括 GitHub Actions
里都能零配置跑起来。实测东方财富有 IP 级限流，连续请求会被
`RemoteDisconnected` 打回，腾讯源能顶上并且前复权口径一致。

### tushare：两个必须知道的坑

**坑一：`pro.daily()` 给的是不复权价，直接拿去回测会看到假跳空。**

实测茅台 2025-06-26 除权：

| 日期 | tushare `close` | tushare `pre_close` | 腾讯前复权 |
|------|----------------|--------------------|-----------|
| 2025-06-25 | 1435.86 | — | 1356.28 |
| 2025-06-26 | 1420.00 | **1408.26** | — |

注意 `pre_close` 是 tushare 已经除权调整过的值 —— 同一个接口里
`close` 和 `pre_close` 分属两套口径。谁直接拿 `close` 序列回测：

```
不复权口径：1435.86 → 1420.00  显示 -1.10%
真实涨跌（官方 pct_chg）：      +0.83%
```

**方向都反了。** 而且这类错误不抛异常、不报错，只是让 MA/RSI/回撤
悄悄失真 —— 分红越勤的票污染越重，最后把垃圾策略验证成好策略。

所以本项目自己算前复权：

```
qfq(t) = raw(t) × adj_factor(t) / adj_factor(最新日)
```

复权算法有独立的验收测试（`tests/test_adjust.py`，10 项断言），
用上面这次真实除权事件做判定：

- 内部一致性：复权后的涨跌幅 `+0.8337%` == 官方 `pct_chg` `+0.8337%`（偏差 0.0000）
- 外部对照：复权价 `1356.28` vs 腾讯前复权 `1356.28`（偏差 0.000%）
- 反向验证：去掉复权后立刻显示 `-1.1046%`，证明确实抓到了这个坑

**坑二：`adj_factor` 是低积分账号的限流重灾区。**

实测同一 token 上，四个接口的门槛差得很远（`python main.py doctor` 逐个戳出来的）：

| 接口 | 官方积分门槛 | 实测状态 | 说明 |
|------|--------------|----------|------|
| `daily` | ≥120 | ✅ **自由调用** | 连续 4 次并发无压力，多标的循环拉取没问题 |
| `adj_factor` | ≥2000 | ⛔ `40203` 频率超限（1 次/小时） | 复权因子 |
| `daily_basic` | ≥2000 | ⛔ `40203` 频率超限（1 次/小时） | 换手率 / 估值 |
| `index_daily` | ≥2000 | ⛔ `40203` 频率超限（1 次/小时） | 基准指数日线 |

注意 tushare 把「积分不够」也报成「频率超限」，报错原文长得一模一样 ——
这就是为什么单看报错容易误判成「我代码写错了」。

**但限流不等于不可用，关键看这个数据多久变一次：**

- `adj_factor` 只在分红除权那天变（一年一两次）
- `index_daily` / `daily_basic` 只追加不回改

所以把整段历史**一次拉下来落盘缓存**、按天/周刷新即可，
日常跑日报根本不会再碰这些接口：

```
复权因子：data/cache/adj_factor/*.json     TTL 7 天
指数/换手率：data/cache/*.csv              TTL 1 天
```

这是「频率限制」和「数据变化频率」匹配后自然消解的典型例子：
**不要跟限流硬碰，先问这个数据到底是多久变一次。**

### 缓存为什么必须带 TTL

默认 1 天。**原因不是省流量，是正确性**：前复权价格在每次分红除权后
会被整体重算，永不过期的缓存会让跨分红日的回测得到自相矛盾的曲线。

复权因子单独用一份 7 天 TTL 的缓存（`data/cache/adj_factor/`），
理由同上：变化频率决定了刷新频率。

## 部署

三种方式，完整步骤见 **[docs/DEPLOY.md](docs/DEPLOY.md)**：

| 方式 | 适合 | 成本 |
|------|------|------|
| GitHub Actions | 只想每天收到看板，不想运维 | 公开库免费 |
| 本机定时任务（cron / 任务计划 / systemd） | 数据不出本机 | 免费 |
| 手动跑 | 研究、调参 | 免费 |

### GitHub Actions

`.github/workflows/daily.yml` 已就绪：

- 每个交易日 18:00（北京时间）自动跑 `analyze`
- 紧接着跑 `reflect` 结算旧判断，把走完验证期的判断变成教训
- 把当日看板、信号台账、反思记忆一起提交回仓库
  （台账是回测样本，记忆是积累下来的全部教训，丢了都是从零开始）
- public 仓库 Actions 额度不限量；private 免费账号 2000 分钟/月也够用

需要在仓库 `Settings → Secrets and variables → Actions` 里配：
`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`，以及任意推送通道的 webhook。

只提交 `data/`，绝不提交 `.env`。

> 记忆的效果是**滞后显现**的：第一天跑起来它什么都不知道，
> 要等到第一批判断走完验证期（`reflect` 结算完）才第一次产生教训。
> 一开始看到"无已知历史"是正常的，不是配置错了。

### CI 在守什么

`.github/workflows/ci.yml` 里有一条容易被忽略但很关键的流水线：
**`stdlib-only` 在完全不装第三方包的环境里跑全部测试**。

项目对外宣称「零强制依赖」，那就必须有一条流水线真的什么都不装去验证它，
否则这个承诺迟早悄悄失效。另外三条：多版本矩阵（3.10 / 3.12 / 3.13）、
以及不阻塞的「网络冒烟」（数据源被限流是常态，不该因此把 CI 判红）
和静态检查（风格问题不该拦住功能合并）。

**`tests/test_workflows.py`：让 CI 自己也被测试。** 这条守卫来自一次真实事故 ——
为了把记忆库/辩论库导到临时目录，曾经把 `${{ runner.temp }}` 写进了
**job 级** `env:`。语法完全合法、缩进无懈可击、本地把 YAML 解析一遍也全过，
但 `runner` 上下文在 `jobs.<id>.env` 里**不可用**：GitHub 直接判「workflow 无效」，
整条流水线**零 job**、立刻变红，而且 **run 日志里一个字都没有**。

这比"测试失败"危险得多 —— 它不告诉你哪里错了，还可能给你假绿灯。
现在这条守卫在本地就能拦下它，并且**每条判据都带对照组**（证明它真的会抓、
且不会把 step 级 `env:` 里的 `runner.*` 误报）。顺带守住另外四件事：
表达式根名合法、每个 job 有 `runs-on`/`steps`、`uses` 都钉了版本、
以及**`tests/` 下每个测试文件都真的被 ci.yml 执行**（加了测试忘了挂 CI，
等于没加）。

六套测试都在 CI 里跑，共 364 项断言：

| 测试 | 断言 | 在验什么 |
|------|------|---------|
| `tests/selftest.py` | 53 | 验证器本身可不可信（指标、费用、边界、判定阈值） |
| `tests/test_adjust.py` | 10 | 复权算法对不对（用真实除权事件判定，非构造数据） |
| `tests/test_lookahead.py` | 27 | 时点门控有没有真的挡住未来数据（含对照组） |
| `tests/test_memory.py` | 116 | 反思记忆会不会漏未来（含对照组，重点在"不该看见时看不见"） |
| `tests/test_debate.py` | 132 | 多空辩论会不会失控（含对照组，重点在"顺序检验真会报警吗"） |
| `tests/test_workflows.py` | 26 | CI 自己有没有真的在跑（含对照组，重点在"零 job 静默失败"） |

六个都是纯标准库、纯离线，所以在 `stdlib-only` 里也能跑。

`stdlib-only` 里还有一步**反向检查**：跑完之后断言 `data/memory/` 与
`data/debate/` 都不存在、`data/ledger/signals.csv` 没被改动。

这条检查是必要的，理由是测试本身会污染真实数据 —— 测试跑一次就写一批假判断，
而**假记忆会被真的注入后续分析**，比假信号危险得多。
所以记忆库支持 `DSA_MEMORY_DIR` 环境变量覆盖位置，CI 全部导到临时目录。

- `.env` 已在 `.gitignore` 里，凭证不进仓库

## 已知限制

- **只用日线**：没有分钟级数据，做不了日内策略
- **基本面维度缺失**：五维评分只实现了能用日线算出的子集。
  基本面/资金面维度故意不做 —— 宁可少做，也不要在回测里
  引入拿不到的历史数据
- **样本量要求**：低频策略（如五维评分）在 2 年区间内产生 20-40 笔交易，
  统计功效偏弱。要得到可信结论，建议扩展到 20+ 标的、5 年区间
- **t 检验只检验均值是否为零**，不做多重比较校正。
  一次跑 20 个策略做对比时，会有约 1 个因运气看起来显著
- **`as_of` 门控只管数据，管不住模型的记忆**：提示词能要求它「别用后来的结果」，
  但没法验证它有没有照做。这是 LLM 回测的固有风险，只能靠
  「只喂指标、不喂叙事」降低暴露面，不能根除
- **反思记忆的门控只管"教训什么时候可知"，管不住教训本身的质量**：
  `learned_date` 能保证一条教训在时点上合法，但 5 条样本里看出的"规律"
  可能就是噪声。样本门槛（≥5）是下限而不是保证 ——
  它降低假规律的概率，不消除
- **记忆只按标的聚合，还没有跨标的的共性总结**：同一类错误（比如追高）
  在不同标的上各记各的，目前靠 `reflect` 的全局错误画像看趋势，
  没有做到"把 A 标的的教训迁移到 B 标的"——那需要行业/风格分组才能做对，
  贸然迁移会把标的特性和普遍规律混为一谈
- **顺序置换检验只覆盖"裁决"这一步，覆盖不了整条链路**：它测的是裁决者
  会不会因为顺序而改变判断。辩手之间的相互影响（后手照着前手的措辞说话、
  被前手的数字牵着走）不在检验范围内 —— 那要跑两遍完整辩论才能测，
  代价翻倍，目前没做
- **辩论的"多视角"来自提示词，不是真的多个模型**：多头与空头用的是同一个
  模型、同一个温度，所以它更像"自我对抗"而不是"两个独立第三方"。
  想真正独立，得给两侧配不同的 `LLM_MODEL`（接口已留出，未做成配置项）。
  这一点会显著影响"辩论有没有增量"的结论，不能含糊
- **权重漂移阈值 `0.20` 是主观定的**：它是个具名常量、测试里有专门用例，
  但阈值本身的合理性没有实证依据。它只是一个"明显漂移"的粗判
- **离线模拟器的裁决天然与顺序无关**，所以 `--mock` 跑出来的
  `order_sensitive` 永远是 `False`。那是模拟器的性质（它只读指标），
  **不代表检验失效** —— 要看到检验真的报警，得看
  `tests/test_debate.py` 里那个「先发言者占优」的假裁决者
- **辩论成本随轮数线性增长，信息增量不线性**：`rounds=2` 已经 6 次调用，
  `rounds=4` 就是 10 次。默认值是 2，往上加之前建议先用
  `compare --strategies llm,debate` 确认它真的值这个价
- **workflow 静态守卫是文本级检查，不是 GitHub 的解析器**：它能挡住
  「job 级 `env` 用了 `runner.*`」这类**上下文可用性**错误（就是真出过的那次），
  但 GitHub 的 schema 远比它严格。**最终判据只有一个**：
  `gh workflow run <file>` —— 文件无效时它以 HTTP 422 原文返回具体行列，
  这是本地唯一能拿到真实报错的通道（run 页面里**什么都没有**，
  因为零 job 的失败根本没机会产生日志）
- **复权基准日的时点只修正了绝对价位**：日收益率序列本来就不受影响。
  想彻底避开基准漂移，回测可以直接用后复权（`adjust: hfq`）——
  它的基准固定在最早一日，不随时间移动
- **LLM 回测既贵又慢**：逐日调用一遍 500 个交易日 × 10 只标的 = 5000 次调用。

  | 路线 | 单次耗时 | 5000 次 |
  |------|---------|---------|
  | DeepSeek | 1~3s | 1.5~4 小时 |
  | 本地 qwen2.5:7b | 16~47s | **22~65 小时** |

  （本地模型热态 16~35s，冷启动要重新把权重读进内存，实测 47s。
  `doctor` 测到的是冷启动值 —— 这是有意的，报乐观数字没有意义。）

  **零成本不等于零代价 —— 本地模型省的是钱，花的是时间。**
  所以本项目里的分工是明确的：

  - **回测**用规则策略（毫秒级，可以随便调参）
  - **实盘信号**用 LLM（每天 5 次调用，1~3 分钟，可以接受）

  prompt 哈希缓存（`data/ledger/llm_cache.json`）能让重跑零成本，
  但首次仍然要跑满 —— 缓存解决的是"调参"，不是"首跑"。
